# Research & Architecture Decisions: TRACE Phase 6 — F07: Upgrade Planner

**Feature**: [spec.md](spec.md) | [plan.md](plan.md)  
**Date**: 2026-10-01  
**Status**: Approved  

---

## 1. Context & Objectives

F07 (Upgrade Planner) converts the structural impact findings and risk assessments from F05/F06 into an **actionable, dependency-ordered engineering upgrade plan**.

To construct an effective, deterministic plan, several architectural and algorithmic questions must be resolved:
1. How to order tasks when software call graphs contain bidirectional or cyclic dependencies?
2. How to map raw AST entities and callers into meaningful architectural execution tiers?
3. How to guarantee deterministic, offline-capable sequencing while allowing optional LLM enrichment?
4. How to model stateful task lifecycle transitions in a concurrent environment?
5. How to partition disconnected components for concurrent developer execution?

---

## 2. Research Decisions & Rationale

### Decision 1: Directed Acyclic Graph (DAG) Sequencing with Tarjan's Strongly Connected Components (SCC)

- **Problem**: Real-world codebases frequently contain circular dependencies (e.g., recursive calls, mutual imports between module helpers). Standard topological sorting algorithms (like Kahn's algorithm) fail or enter infinite loops when cycles exist.
- **Decision**: 
  1. Construct a directed task graph $G_{plan} = (V_{task}, E_{dep})$.
  2. Run Tarjan's or Kosaraju's Strongly Connected Components (SCC) algorithm to detect any cycle subgraphs.
  3. Collapse each strongly connected component containing $>1$ node into a composite "Co-dependent Task Batch" within a condensation DAG.
  4. Perform topological sorting on the condensation DAG using Kahn's algorithm (in-degree tracking).
  5. Expand composite nodes back into adjacent sequential steps, flagging them with `is_circular: true` and adding a warning that they require simultaneous refactoring.
- **Rationale**: Guarantees $O(V + E)$ linear-time execution, eliminates any possibility of infinite loops, and provides clear visibility into circular architectural debt.
- **Alternatives Considered**:
  - *Arbitrary cycle breaking (dropping random back-edges)*: Rejected because dropped edges hide real architectural dependencies from developers.
  - *Failing the analysis on cycles*: Rejected because circular dependencies are common in legacy codebases and TRACE must assist in migrating them, not crash.

---

### Decision 2: 7-Tier Architectural Precedence Ordering

- **Problem**: A pure call-graph topological sort alone is insufficient because non-code files (YAML configs, documentation) and integration tests do not have standard AST call edges, yet they must be sequenced after code changes.
- **Decision**: Define a strict 7-tier architectural precedence hierarchy:
  1. `CONTRACT_API`: Route definitions, API contracts, public request/response schemas.
  2. `CORE_LOGIC`: Internal domain services, core business logic, classes, functions.
  3. `DATA_MAPPING`: Database models, ORM mappings, Alembic/SQL migrations.
  4. `CONSUMER_HANDLER`: Webhooks, async workers, Celery tasks, event listeners (depth-1 callers).
  5. `CLIENT_UI`: Frontend views, client wrappers, downstream UI callers.
  6. `INTEGRATION_TEST`: Test suites, unit tests, and validation targets.
  7. `DOCUMENTATION_CONFIG`: CI/CD workflows, Dockerfiles, environment files, Markdown docs.

  Dependency edges $E_{dep}$ are generated by combining explicit call relationships ($u$ calls $v \implies v$ must update before $u$) with tier precedence ($tier(v) < tier(u) \implies v$ precedes $u$).
- **Rationale**: Aligns directly with software engineering best practices: change contracts and core logic first, then update downstream consumers and persistence, then validate with tests, and finally update documentation.

### Decision 3: Disconnected Subgraph Partitioning for Parallel Execution Streams

- **Problem**: In microservices or modular monoliths, a single version upgrade might affect two completely independent areas (e.g. `PaymentService` and `NotificationService`). A single linear list implies one developer must wait for the other.
- **Decision**:
  - Compute the Weakly Connected Components (WCC) of $G_{plan}$.
  - Assign each disjoint component a unique `parallel_group_id` (e.g. Stream 1, Stream 2).
  - Within each group, enforce topological ordering. Across different groups, tasks can be executed concurrently.
- **Rationale**: Allows engineering leads to partition tasks across multiple developers or feature teams without fear of blocking dependencies.

---

### Decision 4: Deterministic Heuristic Baseline with Optional OpenRouter LLM Enrichment

- **Problem**: TRACE Constitution Principle II mandates deterministic analysis before probabilistic inference, and Principle VI mandates a Free-First architecture.
- **Decision**:
  - **Deterministic Track (Default)**:
    - `reason`: Synthesized from syntax delta inference (e.g. "Signature changed in lines 10-15: parameter added") and call hierarchy distance.
    - `expected_changes`: Formulated from syntax patterns (`def`, `return`, `raise`) and caller site updates.
    - `required_tests`: Looked up directly from Neo4j `TESTED_BY` relationships or test file matching.
    - `risk_level`: Inherited directly from F06 evaluated risk profile.
  - **Online LLM Track (Optional)**:
    - If OpenRouter API key and model are provided, prompts the model with entity context, diff snippet, and caller distance to enrich `reason` and `expected_changes` with natural-language architectural refactoring tips.
    - If OpenRouter fails (timeout, rate limit), automatically falls back to the deterministic baseline with zero downtime.
- **Rationale**: 100% offline capability, zero cost, reproducible results, and zero external dependency risk.

---

### Decision 5: Authoritative PostgreSQL Persistence with File Artifact Cache

- **Problem**: Upgrade plans are stateful operational entities whose task statuses are modified by developers over days or weeks. However, the full graph evidence payload can be large.
- **Decision**:
  - Store core operational state in PostgreSQL (`upgrade_plans`, `upgrade_tasks`, `task_dependencies`).
  - Store full task evidence (complete diff snippets, graph paths, Mermaid diagrams) as a versioned JSON artifact in `.trace/artifacts/plans/{plan_id}.json`.
  - When querying task lists for the UI, read lightweight task metadata from PostgreSQL; load heavy diff snippets on demand when expanding a task card.
- **Rationale**: Fast database queries, relational integrity for status transitions, and low memory overhead.

## 3. Technology Stack & Component Mapping

| Component | Responsibility | Tech / Library |
| :--- | :--- | :--- |
| **Domain Layer** | Aggregates, value objects, lifecycle enums | Pure Python `dataclasses`, `StrEnum` |
| **Planner Engine** | DAG construction, Tarjan SCC, Kahn's topological sort | In-memory adjacency graph, pure algorithmic |
| **Reasoner Layer** | Dual-track heuristic delta rules & OpenRouter client | Standard library `urllib` / existing `OpenRouterLlmReasoner` |
| **Persistence** | Relational state & status tracking | SQLAlchemy 2.0 (asyncpg) + Alembic migration |
| **API Layer** | REST endpoints & request/response validation | FastAPI + Pydantic v2 |
| **Observatory UI** | Interactive task checklist, DAG view, status toggles | Streamlit + standard components |
